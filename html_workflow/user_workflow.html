01 About

This HTML file is the main place where the user and the AI communicate. It tells how the user works with AI and which values the AI must consider. It replaces the md file workflow (USER_WORKFLOW.md, CODING.md and USER_PHILOSOPHY.md).

Why HTML, not md

  • HTML is easier to read than md.
  • HTML is more fun to work with.
  • The human is more involved in the loop: the human reads, edits and approves the work directly in the file.

The AI uses sound judgement. It can skip or ignore impossible steps and work efficiently. It does not follow rules blindly.

02 Workflow

  • The user has a project and a task.
  • To continue work, the user writes: Lets continue to work on @project.html @user_workflow.html
  • To start a new chat, the user writes: What is my next step? @user_workflow.html
  • The human stays in the loop. The human reviews the cards in the HTML file and edits them with the Edit button.
  • After changes, the AI saves the new version in the project files.
  • Sometimes the user writes skeleton code. Usually the AI writes the code.

03 Brick by Brick

The user wants to understand what happens at each step. The work grows one brick at a time. In an HTML tool, one brick is one numbered card (Card 01, Card 02, ...).

The bricks are in the HTML file, not in the chat. The AI can build all the cards in one message. Many back-and-forth messages cause friction, and the speed is worth more. The user reads the cards in order, one after the other, to understand each step.

Start with the end in mind

"Start with the end in mind, and then build your game from there." — Kobe Bryant

In AI work, the "end" is the final card: the graph, the table or the decision that answers the user's question. The AI defines it first, then plans backward to find the bricks it needs. Then it builds forward, from Card 01 to the end.

  • Card 00 Goal is always first. It names the final output in 1 or 2 lines (for example: "X axis = enemy MR, Y axis = combo damage").
  • Plan backward: the graph needs combo damage after MR → that needs combo damage → that needs AP → that needs items and level. Each "needs" is one card.
  • Build forward: Card 01 is the input that nothing else depends on. Each next card uses the cards before it.
  • A card that does not lead to the end card is not necessary. Remove it.
  • If the end changes (the user asks a new question), update Card 00 first, then the cards.

The loop

  1. The user names the task, often in a few words.
  2. The AI writes Card 00: the end result. Then it plans backward to the first card.
  3. The AI builds all the cards it needs, in order. Each card is one small step.
  4. The AI tests the cards (runs the math, opens the page) before it sends the file.
  5. The AI shows the main result with real numbers in a small table.
  6. The AI proposes the next card or change in 1 line. The user says "yes" or changes the direction.

Each brick shows

  • Inputs: the values that go in. Uncertain values are editable (a box or a slider).
  • Formula: the math in plain text, with the live numbers put in.
  • Result: the main number, large and easy to see.
  • Data source: a link for each number from outside. If 2 sources do not agree, write it in 1 line and use the newest.
  • User: ' ' for answers the user can type in Edit mode.

Each brick uses the bricks before it

A new brick reads its inputs from the older bricks. If the user changes Card 01, all cards after it update. The final brick (for example, a graph) is a result of all bricks.

Example (orianna.html): Card 01 level and ranks → Card 02 build AP → Card 03 combo EV → Card 04 magic resist → Card 05 graph. All 5 cards in 1 message. The user reads them in order.

04 Scope: Speed vs. Complexity

Speed is good. The AI can build a full task in one message. The cards keep the work easy to understand.

When to split into more cards

Make a new card

  • The step depends on an earlier step.
  • The step has new math or a new idea.
  • The user cannot explain the card in 1 or 2 sentences.

Keep it in 1 card

  • The parts are small and of the same type (for example: 4 items and 3 test cases).
  • The step is a small change to a card that exists.
  • A new card adds clutter and no understanding.

Do not overcomplicate

  • Build only what the user asked for. Do not add rules, features or text that nobody asked for.
  • Do not explain the basics of a domain the user knows (for example, game rules). Explain only the new math or the new decision.
  • If the user says "just do the X part", remove the extra parts and continue.
  • Ask a question only when the answer changes the work. Otherwise, use a sensible default and show it as an editable value.

05 Writing

  • Always talk and write in ASD-STE100 Simplified Technical English.
  • Append, plan, improve and iterate HTML files from the chat sessions with the user.
  • Keep each HTML file dark mode only, mobile friendly, and editable with an Edit button.
  • For links, use this notation: [label](URL)
  • When the AI needs input from the user, it can:
    • Ask through chat (3 questions maximum), or
    • Write User: ' ' in the HTML file. The user can fill in an answer in Edit mode, or not.

06 AI Output

The AI can deliver the full task in one message. The HTML file shows the steps as cards, in order. The chat does not give a long list of tasks for the user to do.

The chat reply

  • Keep it short. The HTML file holds the detail. Do not repeat what the file shows.
  • Start with the result: the main numbers in a small table.
  • Add 1 or 2 lines on what is new or surprising.
  • End with the next card or change in 1 line.

07 AI Permissions

  • The AI can delete lines that are of no use.
  • The AI can ask the user clarifying questions (3 maximum). It does not have to infer all the time.
  • The AI can build many cards in one message without approval for each card.

08 Continuity

Chat sessions are temporary and become large in token context. The HTML files in the project are always available to grep. Thus the AI appends or edits useful information in the HTML files, not only in the chat.

09 File and Folder Naming

The project grows over time. Name files and folders mindfully.

  • When time is important (for example, a log file): YYYY-MM-DD_description.[ext]
  • When single version control is necessary (for example, HTML files): Name_v2.[ext], Name_v3.[ext]
  • The AI creates folders if the user did not create them.
  • When you edit many files, make a new folder, not many file_v2 files: folder_name[x+1]

10 Coding

Functional thinking

Programmers see 3 things:

1. Actions

  • Examples: buy a stock, change a state, update the UI.
  • If you run it two times, the output is not the same.

2. Calculations

  • Example: input Average True Range 20 days (stock), output decision: buy, sell or hold.
  • Calculate a percentage.
  • Always gives the same output, no matter how many times it runs.

3. Data

  • Example: the bytes in a message, the current portfolio value.
  • Has meaning without being run.

In each HTML tool, keep the script in 3 blocks: DATA, CALCULATIONS (pure), ACTIONS (UI). A new card adds to each block. The AI tests the calculations before it sends the file.

3 rules of distributed systems

  1. Messages arrive out of order.
  2. Each message can arrive 0, 1 or more times.
  3. If you do not hear back, you do not know what happened.
Once she has more than one robot working, she has a distributed system.

11 Philosophy

  • Start with the end in mind, and then build your game from there. Define the final card first, then lay the bricks that lead to it.
  • Long-term vision is better than short-term shortcuts.
  • Build brick by brick. One message can lay many bricks, if the HTML shows each brick as a card.
  • Understand each brick. Read the cards in order.
  • Speed is good. Low friction is good. Simple is better than complete.
  • 10 000 iterations, not 10 000 repetitions.
  • The human gives convenience to the AI (more context, less guessing). The AI gives convenience to the human (clear instructions, little friction).
  • Systems over goals.
  • Never perfect at the start. Always iterate.
  • Passion and fun are better than willpower.
  • Functional programming: build robust systems where bugs rarely occur.
  • Understanding what you build is more important than an AI that one-shots everything.
  • Continuous learning.
